# xv-agents

Skills for the seven agents of Xtreme Vibing (XV): the watch, the forecaster, the scenario agent, the maker, the cleaner, the guardian, and the listener. Each agent is a skill in the open Agent Skills format, so any harness that reads skills can run it: Claude Code, Codex, Cursor, opencode, a local model through opencode. Beside the skills are Python scripts for the parts a check can hold (the test wall, the boundary picture, the spend, the slice record, the standing orders) and GitHub Actions examples that run them in CI.

It is not a plugin and not any one vendor's subagent format. v0.1 was built from a plan without use. The versions after it are earned by use.

XV is the method. This repo is the mechanics: how the agents run, what they may not do, and where they hand back to a person. The method is written up at [xtremevibing.com](https://xtremevibing.com/); the block below is the short form, generated from the same source as the site.

The method is written up at [xtremevibing.com](https://xtremevibing.com/): [the summary](https://xtremevibing.com/), [the map](https://xtremevibing.com/map/) of values, principles and practices, [the loop](https://xtremevibing.com/loop/) one turn of delivery runs through, and [the agents](https://xtremevibing.com/agents/). This is the map in brief, as of 2026-10-21.

**Values**

- **Build for users.** Value is the experience of the person using the software. Understanding users and creating value for them is the job of everyone on the team. Work that is not for their good is refused.
- **Be empirical.** We decide from evidence of real use, not from what we expect. A decision about what the user experiences is void without a recent session with users or a packet from real use. Prototypes are run and compared, not argued. Standards are earned by misses. Budgets are corrected by what the work actually spent. The process itself is a hypothesis: we start with the best we know and refine it as we work. Everyone on the team is learning, by doing.
- **Invest in trust.** The team must trust each other and the system they use to build the system. The people who fund the software must trust the team with the product. Trust is earned, and it is necessary for speed.

**Principles**

- **Decide from evidence.** Two or more people work through the same packet and decide.
- **Lead with conviction.** One person who is accountable decides from experience, responsibility, and judgment.
- **Go and see.** Lean's genchi genbutsu: go to the real place and look at the real thing before you decide.
- **Ship at will.** The gate is released to the person. The harness sets the conditions: red before green, the test wall, the three agents, and a build that returns in minutes.
- **Own the result.** A person is responsible for the consequences of every change, including one made entirely by agents.

**Practices of the team**

- **The shared operating picture.** The team's current understanding, written down: the users, what the system is right now, and ideas for how it can better represent the vision.
- **The shape.** The structure of the system as the team can observe it: design concerns such as coupling, and runtime concerns such as response time budgets.
- **The value queue.** One person ranks the work by customer value, so the ranking is a decision and the product stays one product.
- **The pitch.** A short page in the repo: what the system does, why, and for whom.
- **Contact.** Sit with the people who use the software, or with data about how they actually use it.
- **Parallel prototypes.** For a change where the scenario does not settle the design, and a wrong design would be felt in use.
- **Attention.** A person who is too tired or spread too thin does not make the call today.

**Practices of the machine**

- **The test wall.** A scenario made executable by the scenario agent, which is never the maker, and shown to fail before the fix.
- **The budget.** A budget on the task, forecast by the forecaster with the engineer who takes it, including an expectation of shape change and its breadth (none, narrow, or wide).
- **The three agents.** Three contexts on one change. The maker makes it work behind the test wall; it may move an old test only when the scenario forces it, with a record.
- **The watch.** The agent that runs the pipeline. It knows the state of every slice, calls each agent in turn with a brief and a fresh context, keeps the log visible to anyone who needs it, and wakes a person on a standing order: the stops in the loop.
- **The fast build.** The merge waits on the pre-merge suite (the commit stage) that returns in minutes.
- **Ship.** An increment that cannot be used by a user is not done.

## The one rule

An agent may stop. It may not decide. A person is responsible for every change, including one made entirely by agents, so the harness is built to hand back, not to approve. There is no agent that says yes. When the conditions are met, nobody else has to say yes either: the person who set the work going merges.

## The agents

| Agent | Its job | It may not |
| --- | --- | --- |
| **watch** | Runs one slice: calls each agent in turn in a fresh context, keeps the slice record, wakes a person on a standing order | Merge, rank, settle a shape, edit the pitch, raise a budget, edit its own standing orders |
| **forecaster** | Forecasts tokens, turns and dollars per harness and model from the team's estimation guide; one line on the gap at close | Set or raise a budget; edit the guide |
| **scenario** | Turns the scenario, or a defect's recording, into a test that fails before the fix | Touch source; be the maker |
| **maker** | Makes the new scenario and every old test green; moves an old test only when the scenario forces it, with a record | Weaken a test; renovate; keep going past the budget |
| **cleaner** | Fixes structure and style against the project's standards and commits | Change behaviour; add an abstraction; add or remove a standard |
| **guardian** | One packet: a shape change, a contradiction of the pitch, any old test that moved, what the change does to the shared picture, each finding cited | Fix, approve, or merge |
| **listener** | The packet from production: complaints, paths no story describes, where the pitch and the behaviour diverge | Rank; open issues in the value queue |

The person-facing skills: `xv-init` writes a starter project layer, `xv-slice` starts a slice, `xv-retro` turns misses into checks, `xv-check` reads the project layer against the core, `xv-promote` moves a learning toward these skills.

## How a slice runs

1. A person starts it: the scenario in words, what it may ignore, a recording for a defect (`xv-slice`).
2. The forecaster forecasts; the engineer sets the budget.
3. The scenario agent makes it red. The watch hashes every test file: that is the wall.
4. The maker makes it green. The wall check fails on any test file that changed without a record.
5. The cleaner makes it right and commits.
6. The guardian writes the packet. A shape change or a pitch contradiction stops it for two people. Moved tests and picture changes go to the person who set the work going.
7. Nothing stopped and the suite is green: the merge is theirs.

Each stop ends the watch's turn and waits for an answer. `xv run <id>` runs the same steps with nobody in the loop and exits with the question, so a slice can start at a desk and finish in CI.

## How it works

### What is in the repo

| Path | What it holds |
| --- | --- |
| `skills/<name>/SKILL.md` | One brief per agent and per person-facing skill. The body is the whole prompt of a fresh context. A skill folder may carry a second file the brief points at: the guardian's `packet.md`, the maker's `prototype.md`, xv-init's `outsider-read.md`. |
| `bin/xv`, `scripts/` | The mechanical parts, Python 3.10 or later, standard library only. `xv` dispatches to one script per command; `xv help` lists them. |
| `defaults/` | The starter project layer that `xv init` copies into a repo's `.xv/`. |
| `ci/github/` | Three workflows to copy into an adopting repo: the wall on every pull request, the guardian's packet as a comment, the listener on a schedule. |
| `docs/` | The protected core (`core.md`), why each brief says what it says (`briefs.md`), the slice record's fields (`slice-record.md`), the harness doc sentences the scripts rely on (`relies-on.md`), what was checked on each harness (`harness-notes.md`), every choice the plan left open (`decisions.md`), and what was borrowed (`borrowed.md`). |
| `evals/` | A fixture repo, the scenarios, the runner, the grader, and the results. |
| `tests/` | The scripts' own tests. `cd tests && python3 -m unittest`. |

### A brief is the whole prompt

Each agent runs in a context that has never seen the others. `xv prompt <agent> <id>` builds that context's entire input: the skill's body, then pointers to this slice (the record, the base commit, the budget, the project files). Nothing is restated that the agent can read itself. The same text goes to a CLI run or to a harness's own subagent.

The CLI for each step is a line in `.xv/config.yml`, a list of arguments with `{prompt}` where the text goes. The default is Claude Code in print mode with the person's own customisations off (`claude -p --safe-mode --disable-slash-commands`), so the brief is the prompt and nothing else is. A step may name a different CLI and model: Haiku for the forecaster, Opus for the guardian, a local model through opencode for the maker. A step set to `session` runs in the person's own harness as a subagent instead, with the same text.

An agent reports back in one block at the end of its final message:

```xv-report
{"agent": "maker", "status": "green", "summary": "...", "moved_tests": [...], "stop": null}
```

The watch applies the report to the slice record. A worker never edits the record itself, because a worker that edits the record can edit its own acceptance. The one exception is a test it moved, which it records with `xv record move` as it goes, so the wall can read the move from disk.

### One step

`xv step <agent> <id>` is the unit of work. It does, in order:

1. Builds the prompt and runs the agent's CLI in the slice's worktree. The maker's run gets the budget as hard caps where the CLI has them (`--max-budget-usd` and `--max-turns` on Claude Code).
2. Reads the spend from the harness's own output (Claude's JSON result, an opencode session export) and appends it to the record: tokens in and out, cache reads and writes, dollars where the harness reports them, turns, wall time.
3. Applies the report. A report that cannot be parsed is recorded as no report, which is a stop, not a crash.
4. Runs the checks that follow that step. They are scripts, and the results go in the record:
   - after the scenario agent: it changed only test files, and the red command fails; then the wall baseline is taken;
   - after the maker and the cleaner: the whole suite, the size of the diff against the base, and the wall;
   - after the cleaner: the standards file is untouched, and the fix was committed;
   - after the guardian: the packet exists, passes lint, and says `yes` or `no` to a shape change and a pitch contradiction;
   - after the forecaster and the guardian, which are read-only: nothing changed but their own output;
   - after any of them: no file only people change was touched (the config, the pitch, the picture, the estimation guide, the rules, the wall's hashes).
5. Asks the standing orders. `scripts/orders.py` reads the record and the config and returns every order that fired and the one that stops, by seat.
6. Commits what the step produced on the slice branch, so the history shows what passed the wall.

Exit 0 means go on to the next step. Exit 10 means a person must answer; the JSON on stdout says which order, which seat, and the question. A missing CLI or a failed script is an error, not a stop: the watch says what failed and does not work around it.

### The slice record

One file per slice, `.xv/slices/<id>.md`, on its own branch `xv/<id>` in a worktree under `.xv/worktrees/`. Fixed fields are front matter so scripts and CI can parse them: who set the work going, the base commit, the forecast and the budget, the red, the wall baseline, each moved test with its reason, the suite's colour, the cleaner's commit, the packet, each step's spend, each stop and who answered it, and the decisions two people made. The scenario, what it may ignore, and the log are the body. The field list is `docs/slice-record.md`. `next` is the step the slice resumes at, so a slice started at a desk can be picked up in CI, or by someone else, from the record alone.

### The wall

After the scenario agent's red, `xv wall baseline` hashes every file matching the test paths in `.xv/config.yml`. After the maker and the cleaner, `xv wall check` compares. A test file that changed or disappeared with no matching entry in the record's `moved_tests` fails the check and stops the slice for the person who set the work going. The wall does not forbid a move; it forbids a silent one. The same check runs as a pre-commit hook on slice branches (`xv wall install-hook`) and in CI against the pull request's base, so it holds on every harness without tool-level hooks.

### The stops

The standing orders are code, not prose, so the watch cannot talk itself past one. Each fires on the record alone:

| The record shows | Seat |
| --- | --- |
| The budget is spent and the suite is not green | the person who set the work going |
| An old test moved with a record, or the picture changed, and the shape did not | the person who set the work going |
| A test file changed with no record | the person who set the work going |
| The same failure repeats, or the diff doubled between two runs of the maker | the person who set the work going; the shape conversation opens |
| The scenario passed before the fix, or the scenario agent touched source | the person who set the work going |
| A worker ended with no report, or a read-only agent wrote | the person who set the work going |
| `shape_change: yes` or `pitch_contradiction: yes` in the packet | two people |
| A budget raised past the team's limit, or a shape change wider than forecast | two people |
| Prototypes ready to pick from | two people |
| The suite is green and nothing stopped | the person who set the work going: the merge is theirs |
| The packet from production | the chief engineer; it does not wait |

A person answers with `xv record answer <id> --by <name> --answer "<their words>" --resume`. A stop for two people takes two names, and the script refuses one. The answer goes in the record verbatim; when two people decided, a decision record is written to `.xv/decisions/` with who took part. A team can name a command in `reach:` to be told of a stop (a chat message, a page); without one, the watch says it in the session or `xv run` exits with it.

### The packet

The guardian writes `.xv/slices/<id>.packet.md`: four sections for its four checks, a front matter with `shape_change` and `pitch_contradiction` (each `yes` or `no`) and the door (`one-way` or `two-way`). `xv packet lint` enforces the evidence rule: a finding that cites no line, rule, project file, quoted line or diff hunk is moved to a "Dropped by the evidence rule" section, where a person can still read it, and it does not count. The boundary picture in the packet comes from `xv boundary`, not from the agent: modules and the import edges between them before and after the change, new outbound calls, tables and surface paths the diff adds or removes. It is generated so that it can be wrong in a way someone can check. A missing or malformed packet is read as `yes` to both, so the change waits for people, never for no one.

### The budget and the spend

The forecaster reads `.xv/estimation.md`, a list of closed slices keyed by harness and model, and forecasts tokens, turns and dollars for each key that has rows. It does not read the source; the guide is its evidence, and where a key has no rows it says so and leaves the number null. The person sets the budget from the forecast, and the maker's run is capped by it. At close, the forecaster writes one line on the gap, and the watch appends one row to the guide with a script. `xv record guide-verify` fails a build where the guide was edited rather than appended.

### Headless and in CI

`xv run <id>` runs from the record's `next` to the first stop and exits 10 with the question. In CI the credentials come from a secret, so `claude -p` needs `ANTHROPIC_API_KEY`; a login session is not available there. The three workflows in `ci/github/` pin a tag of this repo, put `bin/xv` on the path, and run:

- `xv wall check --base <base>` and `xv record guide-verify` on every pull request;
- `xv guard --base <base>` on every pull request, which runs the guardian on the slice record in the change, or on the bare diff when there is none, posts the packet as a comment, and fails the check only when the packet calls for two people;
- `xv listen run` on a schedule, which gathers errors, usage and feedback from the sources in the config, runs the listener, fails if the packet ranks, and opens a pull request that hands the packet to the chief engineer.

None of the jobs can approve or merge; the guardian's job has no permission to.

### The project layer

What a team adds to shape the agents for its own system lives in `.xv/`, committed in its repo, shared by everyone on the project and every harness they use:

| File | What it holds | Who writes it |
| --- | --- | --- |
| `config.yml` | Test command and paths, source roots, the CLI per step, seats, limits, listener sources | people |
| `pitch.md` | What the system does, why, for whom | people, from an interview |
| `picture.md` | The shared operating picture: users, what the system is now, decisions that bind, what is in motion | an outsider read an agent writes, corrected and checked by a person |
| `standards.md` | The cleaner's rules, each with the miss it came from | a person accepts each one from a packet or a retro |
| `rules.md` | Facts an agent cannot infer: commands, paths, conventions | people, or a retro |
| `estimation.md` | One row per closed slice | the watch, append-only |
| `learnings.md` | Open learnings waiting for a second sighting | a retro |
| `decisions/` | What two people decided, and who | `xv record answer` |
| `slices/`, `recordings/` | The records and the packets; a defect's recordings | the watch and the agents |

It may add a rule, a fact, an example or a standing order. It may not relax the core: the contexts kept apart, the scenario agent never the maker, a test moves only with a record, the guardian's four checks, the stops, the may-not lists (`docs/core.md`). `xv check` reports a line that reads as a relaxation, a harness file that would shadow a shared skill, every entry with the miss it came from, and a harness doc sentence a brief relied on that is gone.

The shared skills are never edited in place. An upgrade is a copy, not a merge, because every project learning is in `.xv/`. A team that must change a brief copies it under a new name, records why in `.xv/decisions/`, and accepts that the copy no longer receives upgrades.

### How the agents learn

A miss turned into a check stops repeating; a miss turned into a sentence may not. So the main path from a miss to a rule is `xv-retro`, run after a slice that stopped, overran its budget, or drew the same guardian finding twice: a fresh context proposes candidates, each tied to a moment in a slice record, and a person picks. A check becomes a slice like any other. A judgement call becomes a line in the standards file. An Open learning seen twice is promoted inside the repo with `xv promote local`, and shared across repos as an issue on this repo with `xv promote draft` and `post`, which is the only command here that writes in public, and only with a person's approval. A change to a brief, a may-not list or a standing order takes two people and a line in `CHANGELOG.md`.

### What was checked on each harness

Claude Code runs a brief as the whole prompt, reports spend in its JSON result, and refuses writes under `.git/`, which is why worktrees live in `.xv/`. opencode cannot drop its own system prompt, so the brief arrives after about 17,800 tokens of opencode's; it reports spend through `opencode session export`. codex has the flags and was not run. Playwright's test agents install without the healer, which repairs a failing test by editing it, the move the wall exists to stop. Versions, dates and what each line rests on are in `docs/harness-notes.md`; the doc sentences the scripts depend on are in `docs/relies-on.md`, and a weekly workflow opens an issue here when one is gone.

## Install

The skills need the scripts on your `PATH`, so clone the repo and link both:

```sh
git clone https://github.com/seanpk/xv-agents ~/src/xv-agents
cd ~/src/xv-agents
for d in ~/.claude/skills ~/.codex/skills ~/.cursor/skills ~/.agents/skills; do
  mkdir -p "$d"
  for s in skills/*/; do ln -sfn "$PWD/$s" "$d/$(basename "$s")"; done
done
ln -sfn "$PWD/bin/xv" ~/.local/bin/xv
```

Use your harness's own skills folder if it is not in that list. Upgrade with `git pull`, or pin a tag with `git checkout v0.1.0`. `gh skill install seanpk/xv-agents --all` also installs the skills (checked with `gh` 2.102.0, where `gh skill` is a preview), but not `bin/xv`, and `--force` overwrites a local edit without warning.

Python 3.10 or later, standard library only. The default agent CLI is Claude Code (`claude -p`); `.xv/config.yml` names a CLI per step, opencode with a local model included.

## Start in a repo

In the repo, ask your agent to run `xv-init`. It writes `.xv/`, the project layer: the pitch from a short interview with you, the shared operating picture from an outsider read you correct, an empty standards file, the estimation guide, and the config. Commit it. Then start a slice with `xv-slice` and run it with the `watch` skill.

For CI, copy the files in `ci/github/`: the wall on every pull request, the guardian's packet as a comment, and the listener on a schedule.

## What the evals show

Every increment was built with an eval against a fixture repo (`evals/fixture/`, a small pantry app) that has a known slice, a known defect, a known pitch contradiction, and a test the maker will want to move. Each scenario runs with the skill and without it, on Claude Code and on opencode with `gpt-oss:20b` on a local GPU. The results are in `evals/results/`. One run per cell, so the numbers are counts, not rates.
