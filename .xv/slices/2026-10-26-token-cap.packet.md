## Findings for the originator

**A. Half of the scenario is not built.** The scenario (`.xv/slices/2026-10-26-token-cap.md:32`) requires that "the forecaster's token forecast and new rows of the estimation guide use the same count". The diff changes only `totals`:

```
scripts/spend.py:168
+        if "cache_read" in s:
+            t["tokens"] += sum(int(s.get(k) or 0) for k in ("tokens_in", "tokens_out", "cache_write"))
```

New rows of the guide still add up the four-count field:

```
scripts/record.py:382
        k["tokens"] += int(s.get("tokens") or 0)  # input, output, cache read and cache write, as everywhere
```

The forecaster forecasts "from those rows. Use the actuals" (`skills/forecaster/SKILL.md:27`), so its forecast stays in the four-count measure. This slice shows the gap: the forecast is 482,000 sonnet tokens, measured with cache reads (record `forecast`), while the 1M cap is checked without them. That is the mismatch #28 was opened to remove. The red test covers only `budget_state`, so the suite cannot see the gap. "May ignore" lets the slice leave old rows alone, but not new ones.

**B. The retro's forecast check now compares two different counts.** At `scripts/retro.py:67-74`, `whole = totals(...)` is now the three-count sum. It is compared with `1.5 * fc`, where `fc` comes from forecast keys in the four-count measure. When cache reads dominate (91.6% of the thundercloud row, from the scenario's own figures), the flag "spent N tokens against a forecast of M" will almost never fire. The retro's budget check on the lines just above stays consistent, because both sides go through `totals`.

**C. Two written decisions now say the opposite.** `docs/decisions.md:25` (19): "Tokens are counted as input + output + cache read + cache write." `docs/decisions.md:114` (77): "One token count everywhere: input, output, cache read and cache write, in the guide, the budget and the retro." The CHANGELOG line (`CHANGELOG.md:7`) does not revise them. `.xv/picture.md:74` says these decisions do not bind on their own, so this does not stop the change. It is now an open disagreement between the docs and the code, of the kind `.xv/picture.md:39-42` keeps track of.

**D. Which count a row gets depends on which keys it has.** `scripts/spend.py:168-171` counts a row with a `cache_read` key as three counts, and a row without one by its `tokens` field. Every reader in `spend.py` writes all four keys (`scripts/spend.py:30-37`), so harness rows are consistent. A hand-written row or an older one without `cache_read` is still counted with its whole `tokens` value. `tests/test_spend.py:33-38` depends on that fallback.
